## 2. bench-smoke：本仓的纯函数微基准

被测函数：`tokenize`（`src/retrieve/interning.ts`，sha256 `8376dd3797c3`）

命令：`node scripts/bench-smoke.mjs`
规模：100 000 次调用 × 7 轮，报**每轮 per-call 耗时的中位数**。

| 轮次 | 三次独立运行的中位数（ms/call） |
|---|---|
| run 1 | 2.311e-3 |
| run 2 | 2.224e-3 |
| run 3 | 2.188e-3 |

- **中位数：2.19e-3 ms/call**（约 2.19 µs）
- 三次运行极差 / 最小值 = **1.06×**，即 ±3% 内
- can-red 自检：空实现中位数 3.8e-6 ms，**分离度 589×**，SIGNAL-OK

选它的理由：`tokenize` 是检索层真正做分词的那一步，无状态、无 IO、输入固定。
它变慢意味着每个召回路径都变慢，而不是某个分支变慢。

## 3. 为什么**不设阈值**

**先有基线，才有阈值。** S2 性能基线（2026-11-09）的教训：50 并发 p95 = 7.26ms 里
**76.6% 是排队**，不是计算。用「并发 p95」当分母，会把排队时间当成自己的预算，
把可见的计算增长说成"可忽略"。

所以 B0 只记基线：**基线是事实，阈值是判断**。判断需要知道正常波动范围，
而那个范围现在还不知道 —— 本仓只测了 3 次，1.06× 的极差说明这台机器上够稳，
但**不足以**支撑「超过 X% 就报警」这种判断（换机器、换 Node 版本、CPU 降频都会改变它）。

## 4. bench-smoke 自带 can-red（为什么它不是一个昂贵的 `console.log`）

脚本内部跑两次：一次真函数、一次空实现 `() => {}`，并断言**真函数的中位数必须显著更高**
（当前门槛 2×）。不满足就打印 `NO-SIGNAL`，而不是装作测到了。

这条自检在开发本脚本的过程中**真的否掉了两个候选**（见各仓脚本注释）：

- memory 第一版候选没问题，但 graft / paradise 的初版分别撞上 1.57× 与 0.44× 的 NO-SIGNAL；
- paradise 那次是我的输入喂错了（函数签名收 `string`，我传了对象，内部第一句就短路）。

**这些都不是函数的问题，是量具在说「你测的东西不对」。** 没有这条自检，
三个仓都会带着一个假基线入库，而它在下次需要判断时给出的是错误的安全感。
