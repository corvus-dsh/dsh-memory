# D9 的形态 ⑧–㉚：门禁失效的二十三种形状（附 ⑭ 取证方法论）

> **D9** 是「门禁不是装饰」这条纪律的反例册：凡是**该红没红、该拦没拦、红了却读不出原因**的，
> 都登记在这里。①–⑦ 在项目报告里；本文件收 2026-11-17 这一天真实发生的五种，
> 每条带实测证据、判据，以及本仓的处置。
>
> 统一格式：**形态 → 实测 → 为什么它会安静地通过 → 判据 → 本仓处置**。

---

## ⑧ 把「离线/构造环境的实测」当成「生产环境的实测」

**实测**：`compaction-guard` 的公式用构造的 preset 验出 `0.6934 → 0.6734`，写进交接方案时成了
「**本 profile 实测生效值**」；而 live 的 `graft_debug_status` 是 `source:"conservative"`、
`effectiveHardAt 0.55`、`reason` 写明 `O=unreadable`（4 个 preset 都读不到 `maxTokens`）。

**区别**：前者证明「**公式对**」，后者才是「**这台机器上算得出**」。

**判据**：任何标「实测」的数字，必须写明「**会话名称、会话代数、在哪个环境测的**」。
三者缺一，那个数字就不是实测，是推断。

## ⑨ 门禁的安装动作本身破坏了门禁

**实测**（2026-11-17，`dsh-memory`）：B0 新增的 CI step 的 `name:` 值里含 `: `
（`- name: Incremental type budget (RESOURCE-aware: no compiler on the runner)`）。
YAML 规定 plain scalar 不得含 `: `，它被当作 mapping 指示符 ⇒ **整个 workflow 解析失败**：

```
run 44002473416   conclusion=failure   jobs=0   check_runs=0
GitHub 上该 workflow 的 name 回落成文件路径 .github/workflows/ci.yml（正常是 CI）
```

⇒ 所有门禁**一条都没跑**，而本地 `npm run check` 全绿（本地从不解析 `.github/workflows/`），
报告里写着「已接线」。

**为什么安静地通过**：CI 确实红了，但**没有 job 日志可读**——没有失败步骤名、没有 error 行，
只有 0 个 job。本地与 CI 双双答不出「门禁到底装上了没有」。

**判据**：任何修改 CI 配置的提交，**必须有一条「配置本身可解析」的判据，且该判据在同一次提交里**。

**本仓处置**：`test/v220-workflow-yaml-safe.test.mjs`（四仓逐字节相同、零依赖、CI 上真跑）。
它扫 `.github/workflows/` 下**全部** `.yml`，三条零误报判据（`: ` / ` #` / tab 缩进），
先**剥引号**再**跳过块标量正文**（否则会放过修复前那一行，或把一大片 shell 全报红），
并带反向用例（引号内与 `run: |` 正文里的同类字符**不许**报）。

## ⑩ 判断「有没有接线」时查了名字，没查实际命令

**实测**：`dsh-observer` 的 `check-readme-counts` 被接在名为 **`Gates (previously unwired)`** 的
step 里（`run: |` 三条命令的第二条）。按 step 名搜索 `check-readme-counts` 得 0 处 ⇒ 判「没接」，
**实际在跑**。同一天还误判了一处：`dsh-graft-slice` 的 `check-docs.mjs` 读的是 `tests`
（环境无关，本来就是对的），被当成「读本地口径」一起报了出去。

**为什么安静地通过**：`name:` 是人起的、可任意命名；`run:` 才是事实。名字与命令之间没有约束。

**判据**：要判断「某条判据是否真的在跑」，**搜索 `run:` 之后的命令，不要搜 step 名称**。
（推论：step 名里别写命令名——那会诱导下一个人用名字去搜索。）

## ⑪ 同一语义的判据有两份实现，口径不同，而没有门禁守护这个一致性

**实测**（同一天，同一语义「文档里的测试数」）：

| 实现 | 读数 | 环境相关性 |
|---|---|---|
| `dsh-graft-slice/scripts/check-docs.mjs` | `/tests (\d+)/` | **环境无关**（`t.skip` 仍计入 `tests`） |
| `dsh-memory/scripts/check-readme-counts.mjs` | `/pass (\d+)/` | **环境相关**（CI 上 13 条 `RESOURCE` skip 不计） |

后者意味着：README 声明「546 / 546」在本地成立、在 CI 上必然红（`pass 533`）——
**同一条断言在两个环境里不可能同时为真**。而 `check-readme-counts` 四仓逐字节相同、
有 FACT 5（同工作区副本哈希）守着，所以**它内部口径错了就是四仓一起错**；
`check-docs` 只有 graft 有，没有任何东西跟它对齐。

**为什么安静地通过**：两份实现各自绿着。一处只在本地绿，另一处真绿——**没有任何东西去问它们是否在说同一件事**。

**判据**：同一语义的判据**只能有一份实现**；多份时必须有**跨仓一致性断言**
（`run-gate.mjs --check-copies` / FACT 5 那一类），且一致性要断言到**读数口径**，不只是字节。

**本仓处置**：`countOf(out)` 成为唯一读数点，`pass + skipped` 为读数：
`t.skip` 计入 `tests`（实测：一个通过 + 一个 `t.skip` ⇒ `tests 2 / pass 1 / skipped 1`），
所以 `pass + skipped` 在本地与 CI 都等于「本仓有多少条测试」。「全绿」由 `fail > 0 ⇒ RED`
独立断言，因此这次改动**没有削弱**判据，只是删掉了「只可能在其中一个环境为真」的比较。

## ⑫ 验收「门禁接线」时，只在本地跑了它，没问「它在 CI 上会不会给出不同结论」

**实测**：B0.1 验收时，在本地跑 `check-readme-counts` 看到
`all 7 checkable fact(s) match. exit 0` 就判「接线成功」。
实际上它比的是**环境相关**的 `pass` 数，在 CI 上必然红 —— 第一次 push 就红了
（run 44006262441，两个 job 都红在 `Documentation counts match the code`）。

**为什么安静地通过**：本地绿是**必要**条件，被当成了**充分**条件。而这条判据的两侧
（README 声明 / 实测数字）恰好只在本地相等。

**判据**：验收一条「接进 CI 的门禁」时，必须回答：**它的断言里有哪些量是环境相关的？**
凡属于下面三类的量，都**不能**作为跨环境断言的输入：

1. 依赖编译器 / 工具链（`typescript`、`sqlite`、外部二进制）；
2. 依赖 git 历史（浅克隆里没有的提交）；
3. 依赖文件系统时序（pid、临时目录名、并发默认值、目录遍历顺序）。

**本仓处置**：README 的计数声明加上**口径限定**（「本地口径；CI 上 13 条 `RESOURCE` skip
也计入此总数，见 `ARCHITECTURE.md` TD-M15」），并保留 `N / N` 自等格式 ——
去掉自等格式等于把断言删掉（判据会「无断言可做」）。

## ⑬ 跨仓一致性判据使单仓 CI 不可独立验证

**形状**：`check-readme-counts` 的 FACT 5 逐个哈希「同工作区」的兄弟副本，**分叉即 FAIL**。
各仓 CI 用 `mv .siblings/<repo> ../<repo>`（`ci.yml:70`）把兄弟 checkout 到 FACT 5 的 `workspaceRoot`
（`check-readme-counts.mjs` 里 `workspaceRoot = new URL('../', repoRoot)` —— **同一个 `../`**），
且不带 `ref:` ⇒ 取兄弟仓**默认分支的已推送版本**。

**实测**（2026-11-17，memory CI run 44010364457）：run 红在 `Documentation counts match the code`，
日志 **403 读不到**。受控实验复现 —— 把兄弟仓的副本换回已推送的旧 blob
（`git cat-file blob 395fe3b78518`，sha256 `939b8bc46634`）：

```
ok   L106 测试数 546 / 546 与实测一致
ok   L537 测试数 546 / 546 与实测一致
ok   README 未声明当前版本 …  ok  ARCHITECTURE.md 的每个数字都有现状/时点限定
FAIL check-readme-counts.mjs 四份副本已分叉：dsh-paradise (939b8bc46634 ≠ ab0a7dcb5456)
```

换回新版 ⇒ 全绿。**失败原因不是计数，是兄弟仓落后。**

**代价（必须接受，不是要修掉）**：

- 改四份副本之一必须**四仓一起推**，不能逐仓验证；
- 推序由依赖方向决定：`paradise`（不 checkout 任何兄弟，唯一可单独验证）
  → `memory` / `observer`（依赖 paradise）→ `graft`（依赖 paradise + memory，最受限）；
- **「先在一仓验到绿再推广」这个策略，对这个判据不成立。**

**判据**：任何跨仓一致性判据，必须写清
（a）它在 CI 上读的是**哪个版本**（默认分支已推送？当前 commit？）
（b）因此它给单仓 CI 引入了什么**前置条件**
（c）满足前置条件的**推序**。

不写这三条的跨仓判据，会在第一次 push 时把「兄弟仓没推」误报成「本仓有问题」。

**本仓处置**：不改判据（它抓到的是真事实），而是把推序写进流程，并保留受控实验作为取证手段。

## ⑭ 取证方法论：审计通道不可用时，构造那个环境（不是跳过验证）

**实测**：memory CI 的失败原因**读不到**（job 日志 403 `Must have admin rights`，HTML 页面 30s 超时），
匿名 API 额度也曾耗尽。但把兄弟仓的副本换回旧 blob 再本地跑一次判据，**一行输出就给出了确定答案**
（见 ⑬ 的对话块）。

**判据**：任何「我拿不到 X，所以无法验证」的结论，先问一句 —— **X 能不能在本地构造出来？**

三种取证通道，按可及性排序（本轮三次 CI 失败各用了一种）：

| 通道 | 本轮实例 | 何时可用 |
|---|---|---|
| **API 可观测** | workflow 的 `name` 回落成文件路径 ⇒ 解析失败（run 44002473416 有 0 个 job） | 有读权限的公开端点即可 |
| **代码可读** | `actualTests = /pass (\d+)/` + `ci.yml` 自述「13 条在 CI 上跑不了」⇒ 断言两环境不可同时为真 | 有仓库读权限即永远可用 |
| **环境可构造** | 替换兄弟仓 blob ⇒ 复现 CI 的 FACT 5 红 | **不需要任何 CI 权限** |

**构造环境的三条纪律**（本轮实践）：先备份 → 做替换 → 跑判据 → **还原并校验 SHA-256 逐字节一致** →
把「还原一致 = True」写进报告。构造是为了**取证**，不是为了**改变状态**。

**附：构造出来的环境 ≠ CI 环境。** 本次实测：模拟浅克隆时漏了兄弟仓（`dsh-paradise`），
多出 1 条与 CI 无关的失败（`bridge: the layer decoding really happens`）；补上兄弟仓后它消失了。
判据：受控实验的结论必须能区分「**被检对象的缺陷**」与「**模拟环境的缺陷**」，
否则实验本身会成为新的假证据。

## ⑮ 「同源文件」靠约定，不靠判据 —— 于是它必然分化

**形状**：`test/run-gate-resource.test.mjs` 的头部写着
「THE SAME FILE IN FOUR REPOSITORIES, ON PURPOSE」，实测却是 **2 种版本**：
`dsh-memory` 239 行（有确定性回退）/ 其余三仓 177 行。**没有任何判据比较过它。**

**后果**（2026-11-17，observer CI run 44014143688）：observer 的 `Test` 步 **2 秒红**，
唯一失败 = `run-gate: a REAL failure still exits 1 (the wrapper is not a blanket pass)`。
根因：177 行版在**浅克隆**（CI 的 checkout 是 `depth=1`）里取 `<sha>~1` 作为 before ref，
而 `~1` 在 `depth=1` 里不存在 ⇒ instrument `exit 2` ⇒ `run-gate` 翻成 `0` ⇒
`assert.equal(code, 1)` 失败。memory 的 239 行走同一条路径，但有「不可测 ⇒ 回退到确定性
cycle fixture」，所以绿 —— **同一个判据，两个仓给出相反结论。**

**对照**：同一批文件里 `run-gate.mjs` 有 `--check-copies` 自校验，`check-readme-counts.mjs`
有 FACT 5，唯独这个测试文件没有。它不是「忘了写判据」，而是「没人意识到它需要判据」。

**判据**：任何自称「四仓相同」的文件，必须在**同一提交**里带一条比较它四份哈希的判据；
否则「相同」只是一句注释。已落地：FACT 5 扩为 `IDENTICAL_ACROSS_REPOS` 清单
（`scripts/check-readme-counts.mjs`、`test/run-gate-resource.test.mjs`），输出点名义上是
**哪个文件**分叉、哪个仓、两个哈希前缀。

**附：CLONE DEPTH 是隐藏的判据输入。** 依赖 `git log -N` / `~1` / `HEAD~1` 的判据，在
`depth=1` 下行为不同。凡使用 git 历史的判据，必须（a）检测 `~1` 是否存在
（b）不存在时回退，或**明确说「没测」** —— 不许把「测不了」写成「测了，结果是相同」
（本轮实测：旧版 `why` 的分类把 instrument 的 `cannot measure … not PURE` 归进了 `was PURE`）。

## ⑯ 只在 CI 里跑的门禁，本地永远发现不了它坏了

**接线有两种程度：接进 CI ≠ 接进本地。**

**实测**（2026-11-17，graft CI run 44019243007）：graft 的 `npm run check` 覆盖 CI 的 11 个步骤，
**漏掉 5 个**：

| CI step | 命令 | 本地 check 有吗 |
|---|---|---|
| #12 | `check-readme-tally.mjs` | ❌ |
| #13 | `verify-bundle.mjs` | ❌ |
| #14 | `git status --porcelain .export-surface.json`（内联 shell） | ❌ |
| #15 | `check-artifact-fresh.mjs` | ❌ |
| #18 | `who-references.mjs --json buildTape`（内联 `node -e` + `/tmp`） | ❌ |

⇒ 它们**从没在本地执行过** ⇒ 本地不可能发现它们坏了。`check-readme-tally` 的解析器与 README
行文错配（三处）就是这样藏到今天的。

**对照 B0 的主题**：「a gate nobody runs is a comment」。这批门禁确实有人在跑 —— 但**不是开发者**。
**跑的人没有修改权，改的人看不到红。**

**判据**：一条门禁的接线完成，要同时满足
（a）在 CI 里跑
（b）在开发者会执行的命令里跑（通常是 `npm run check`）
（c）两者跑的是**同一个脚本、同一组参数**。
只满足 (a) 的门禁，其失效周期 = 两次 CI 失败之间的时间。

**本仓处置**：5 条全部接进 graft 的 `check`；其中两条原是 ci.yml 的**内联 shell**
（`/tmp` 在 Windows 上不存在，本地根本不可复现），改成
`scripts/check-export-baseline.mjs` 与 `scripts/check-symbol-lookup.mjs`，**ci.yml 与 check 共用**；
`v129` 的分类表补两条 GATE。代价：`npm run check` 197s → **297s**（tally 会再跑一次套件；
让 tally 复用 counts 的测量结果留到 B4 性能批次）。

## ⑰ 解析器与文档行文的配对，没有测试守护

**读文档的判据，与它读的那段行文之间，是「约定」不是「契约」。**

**实测**：`check-readme-tally.mjs` 的正则要求

```
**850/852**（无空格） + （2 条…跳过…）（数字不在 ** 里、中文「跳过」）
```

README.md 实际是

```
**850 / 852**（有空格） + （**2 条 skipped，不是 failed**）（数字在 ** 里、英文）
```

三处全部错配 ⇒ `claims found: 0` ⇒ FAIL。

**为什么没早发现**：
（a）判据头部注释里固化的样本是**旧行文**（`**696/698**（2 条待裁定跳过）`）；
（b）判据只能在 CI 里跑（见 ⑯）；
（c）它自己的测试 fixture 用的是**同一批旧行文** —— 所以**测试绿、真实文档读不到**。

**判据**：解析文档的判据，其测试 fixture 必须包含
（a）当前文档里**真实存在**的那几行（**读出来**，不是抄一份 —— 抄的副本会随文档漂移而一起漂）
（b）至少两种「同一语义、不同排版」的变体。
否则 fixture 只证明「解析器认识它自己的样本」。

**本仓处置**：v128 补三条用例 —— 第一条**读真实 README 行**并断言本仓与 memory 两份声明都被解析出、
三数自洽（文档一改，这条就红）；第二条四种排版变体；第三条「没有声明 ⇒ 0 条」，
保住「找不到 ⇒ FAIL」那半条规则。

## ⑱ 新增测试/脚本文件前必须检查编号是否已被占用

**实测**（2026-11-17）：让执行者建 `v220-workflow-yaml-safe.test.mjs` 时没有先查编号，
而 graft 早已有 `v220-audit-f1-f2.test.mjs`。两个文件同时存在且都能跑，CI 是绿的 ——
**功能没事，但「v220 是什么」不再可回答**。而且新文件是**四仓逐字节相同**的，改名要四仓同步一轮
（见 ⑬ 的推序代价）。

**判据**：`ls test/v<N>*` / `ls scripts/*<N>*` 先查。撞车不阻塞，但它把编号从「一个身份」变成
「一个前缀」，而下一个人会按编号去引用。

**处置**：B4 收编（那一批本来就要动四仓），改名为当时实际空闲的号。

## ⑲ 注释声称的接线，必须有一条测试走过那条路

**实测**（2026-11-17，graft `1c7118a` → `568cfaa`）：

B1-5 第一步把 `filterRejectedConstraints`（函数）、否决记录 store、8 条测试全部落了地，
`src/index.ts` 的注释写着：

> `filterRejectedConstraints` — the REJECTION track. **It is applied by the extraction path**

而实测 `grep filterRejectedConstraints src/` 只有两处：**这条注释，和函数定义**。没有调用点。

于是 v222 的 ①⑤⑦ 证明的是「**如果**调用它，它会正确过滤」，而不是「它会被调用」。
**这是一条绿得很漂亮的测试，守着一个没人走的分支，外面包着一句说它在被走的话。**

**为什么这比「忘了接线」更糟**：一句「已经接了」的注释会让下一个读代码的人**停止寻找接缝**。
沉默至少还会让人去找。所以这类注释属于 D9 家族里最坏的一种 —— 它不是没有信息，
它给了一条错误且可执行的信息。

**判据**：
1. 任何「X 由 Y 应用」的注释，必须有一条测试**从 Y 的公共入口**（这里是 `buildInjectionPlan`，
   工具层唯一入口）出发，而不是把记录手传给纯函数 X。
2. 这类测试必须能**证红**：把接缝摘掉，它要红。本次实测：摘 `workspace` 参数 ⇒ v224 ①⑥ 红；
   摘 `manual` 参数 ⇒ v224 ③ 红；恢复后 15/15 绿且 `index.js` 逐字节回到 919480。

**本仓处置**：`test/v224-constraint-wiring.test.mjs` 七条，其中 ①②③⑥ 都从 `buildInjectionPlan`
出发。同一次还补了 `graft_constraint` 工具的接线测试（add/reject/promote/demote 四动作 +

## ⑳ 判据给出的建议，必须能在判据自己的执行环境里做到

**实测**（2026-11-17，graft `5bba1cf`）：

`verify-bundle.mjs` 的失败消息写着
「add `[export-change]` to the commit message if intended」，而它读的是：

```
process.env.GRAFT_COMMIT_MESSAGE ?? ''      ← 由 workflow 设置
process.env.GITHUB_HEAD_COMMIT_MESSAGE      ← 同上
```

**开发者照着它的话做了（提交信息里写了 `[export-change]`），再跑 `npm run check`，仍然红** ——
本地没有任何文档说要设哪个环境变量。唯一能让本地链变绿的办法是手工导出 CI 变量。

这是 ⑯ 的极端形态：不只是「本地跑不到」，而是**判据自己给出的补救办法在它自己的执行环境里
不可执行**。开发者学到的不是「照做」，而是「这一步反正过不了」。

**修法**：环境变量仍然优先（CI 上它才是权威副本 —— squash 之后 merge commit 的信息不是作者

是关于 `git log` 的**历史深度**，而这里只读一个提交）。

**判据**：任何失败消息里的「请做 X」，都要有一次在**开发者实际会跑的那个命令**里从红到绿的记录。
做不到的话，那不是建议，是免责声明。

## ㉑ 覆盖分支 ≠ 覆盖默认分支：主路径上的绕道

**实测**（2026-11-17，graft B1-5 收尾）：

`buildInjectionPlan` 里把两条轨道接进抽取分支：

```js
constraintsOverride !== undefined
  ? selectConstraints(override.map(…), budget)                     ← 直通，不过两个 store
  : extractConstraintsDetailed(events, budget, { workspace, rejections, manual })
```

看起来只是优化（「调用方已经有规则了」），实际上 **`constraintsOverride` 是主路径**：
`graft_slice_and_inject` 在 L6862 先算 `fastConstraints = extractConstraints(raw.events)`，
再把它当 override 传进来（v5.2 为了不阻塞关键路径，把 LLM 抽取挪到后台）。

所以真实的切片**从来没有读过否决记录和主动声明**。`graft_constraint` 是一个写文件、
而没有人读那个文件的工具。

实测（`probe-v226`）：reject 一条规则 → 落盘成功（store 1 条，`rejectionCount: 1`）→
再切片 ⇒ `plan.constraints` **仍然包含被否决的句子**。

**这一条的教训比 ⑲ 更深**：⑲ 是「注释说接了、其实没接」；㉑ 是「接了，但接在了不是默认走的那一支」。
后者的测试会全绿 —— 因为测试通常直接调纯函数或走 `extractConstraintsDetailed` 那一支，
而生产走的是另一支。

**判据**：
1. 一个 `a ? X : Y` 的两支，若 X 是新接的行为、Y 是旧行为，必须**逐一确认哪一支是生产默认**。
   `grep` 调用方，看有没有一个参数让 X 恒不成立。
2. 端到端测试必须走**工具层入口**（`graft_slice_and_inject`），不是走内部函数。
   v226 就是为了这个而存在：它的断言打在渲染后的 system prompt 字符串上。
3. 证红要分别做：摘过滤 ⇒ ① 红；摘主动轨 ⇒ ②③ 红。

**本仓处置**：`constraintsOverride` 保留（它是合法的性能决定），但**两支都汇到同一个池**，
再统一过 `applyManualConstraints` → `filterRejectedConstraints` → `selectConstraints`。
未来若有第三个分支，它有一个显眼的「该去哪儿」，而不是一个显眼的「可以忘」。

## ㉒ 精确匹配制造的假红是便宜的，模糊匹配制造的假绿是昂贵的

**实测**（2026-11-17，v226 第一版）：

测试里 reject 的文本是 `必须…文档`（**不带**句号），而抽取出的候选项是 `必须…文档。`（**带**句号）。
精确文本相等 ⇒ 不匹配 ⇒ 记录命不中 ⇒ 规则留在 prompt 里 ⇒ 测试红，
读数像「整条链路是断的」。**断的不是链，是我比错了字符串。** 修 5 分钟。

**为什么这条值得单独记**：如果过滤用的是模糊匹配（前缀 / 子串 / 去标点比较），
同一条测试会在「把邻近句子也一起否决」的实现上**转绿** —— 那个 bug 会留到生产，
而且表现为「用户说这条别用，结果相邻那条也不见了」，安静、难复现、归因困难。

所以「精确匹配」不是实现细节，它是**这条测试能发现 bug 的前提**。

**判据**：
1. 约束 / 规则 / 否决这类「指着一个具体字符串」的匹配，默认用**精确文本相等**。
2. 需要模糊时，必须在同一条测试里同时断言「**邻近文本不被误否决**」——
   否则模糊化把假红换成假绿，而你只会看到它变绿。
3. 一条红测试首先要问的不是「实现哪里错了」，而是「**我比的是不是同一个东西**」。
   本次假红与 ⑲㉑ 的区别：那两条是**真缺口**，这条是**假证据**。两者的处置完全不同，
   而混淆它们的方向是「改测试让它绿」——那会把假红变成真绿，同时把真缺口埋掉。

## ㉓ 同名目录不是同一个目录：`profiles/desktop/.dsh-memory` vs `.dsh/.dsh-memory`

**实测**（2026-11-17）：

同一个 profile 下有两个都叫 `.dsh-memory` 的目录，内容完全不同：

```
C:\Users\…\.dsh\profiles\desktop\.dsh-memory      ← 活 store，任务图在这里（14,081 字节 / 18 节点）
C:\Users\…\.dsh\.dsh-memory                       ← 另一份，任务图不在里面
```

**读者会困惑，而困惑的代价是真实的**：查「任务图写到哪了」的人先看到的是外面那一份，
在里面找不到 `task-graph.json`，于是得出「没写进去」的结论 —— 而这个结论看起来有证据
（他确实 ls 了那个目录，确实没有那个文件）。**证据是真的，问的是错的那个目录。**

**判据**：
1. 报一个路径时，报**能 `Test-Path` 成功的那一条完整路径**，不要报「.dsh-memory 里」。
2. 「找不到文件」永远先当成「找错了地方」，再当成「没写」——
   与 ⑭ 同族：仪器的「找不到」会被显示成一个看起来合法的结论。
3. 两个同名目录同时存在时，文档里必须点名哪一个才是活 store，并写清另一个是什么。

## ㉔ 为了做「正确的事」而触发的写入，可能抹掉另一件刚做完的事

**实测**（2026-11-17，同一次会话内，间隔 **23 毫秒**）：

```
10:11:26.414  第一次 knowledge_harvest 写入（写盘 task-graph.json：18 节点 + 8 条长期约束 + v3 字段）
10:11:26.437  task-graph.json 的 mtime
              ⇒ 此刻 persistentConstraints 已不存在，18 个节点全部退回 11 个 v1 键（v3 字段 0/18）
              ⇒ history 只剩 2 条（都是我写盘时写的 lock-goal + add），且没有 author 字段
```

**代码链**：

```
src/index.ts:1433  markHarvested(resolved.memoryDir, activeNodeIdsForHarvest(...))
src/graph.ts:713   markHarvested → readGraph → 改 harvestedAt → persist 写回
```

**为什么这是独立的一条（不是 ㉓ 的重复）**：

| | ㉓ | ㉔ |
|---|---|---|
| 症状 | **找不到**（读者困惑） | **丢掉**（数据损失） |
| 触发 | 人查错了目录 | 代码走了「读-改-写」的既有路径 |
| 严重性 | 可恢复，成本是时间 | 不可见、无报错、不可恢复 |

㉔ 的恶劣之处在于：**触发它的那次写入是完全正确的**。三个 done 节点需要盖 `harvestedAt`，
harvest 是系统提示要求的动作，`markHarvested` 做的事一字不差。**没有任何一步是错的，
数据就是没了** —— 因为 `persist` 走的是白名单重建，而白名单里没有新字段。

**判据**：
1. 任何「读-改-写」的持久化路径，必须先证明「**它不改的字段会原样保留**」，
   而不是假设它会。**尤其是「打个时间戳」这类看起来无害的写入** —— 本次就是它。
2. 这个证明的形式是**往返保真测试**：造一份含全部字段的图 ⇒ 走一遍该写入路径 ⇒
   逐字段比对。只验「读回来对」（正向）不够，必须验「经过既有写入路径后仍在」（反向）。
   这是 ⑫ 的镜像：⑫ 是「验收只验了正向」，㉔ 是「**代码**只实现了正向」。
3. 新字段落地时，配一条「经过**所有**既有写入路径后仍在」的测试，而不只是「写进去能读出来」。
   本次的缺口正是：v3 字段写了、读得出来、**但没测过 harvest**。

**与 ⑨⑩⑪ 的关系**：那三条是「保证本身没写全」；㉔ 是「保证写全了，但另一条既有路径不认识它」。
白名单（⑨ `carryUnknownKeys`）能让**新代码**带上未知字段；但如果**另一条路径**（`markHarvested`）
自己在重建对象，它不会去问白名单。**一条判据只能守住它自己那条路。**

## ㉕ 行数上限会逼出「按语义拆」而不是「按行数切」

**实测**（2026-11-17，T1 的 v3 字段落地）：

第一次把 v3 校验**内联进 `graph.ts`** ⇒ `681 → 1,351` 行 ⇒ 被 800 行上限拒绝。
天花板只能降不能升，所以必须拆。拆的结果：

```
graph.ts      801 行   —— owns the GRAPH
graph-v3.ts   689 行   —— owns the FIELD JUDGEMENT
```

**标准不是「前 689 行 / 后 801 行」，而是上面那两句话。**

**为什么这条对 B4（拆巨石）直接可用**：行数上限是**外部约束**，它只告诉你「必须拆」，
不告诉你「在哪切」。而人在压力下最容易做的恰恰是「按行数切」——
那会得到一个能编译、能过门禁、但**没有任何一个人能说出它负责什么**的文件，
下一次修改就要在两个文件之间反复横跳。

**判据**：
1. 当行数上限逼你拆文件时，先回答「这两半各自负责什么」。
   **答不出来，说明还没到该拆的时候**（或者该拆的不是这里）。
2. 拆完的每个文件，头注释里必须有一句 `owns the X`，且这两个 X 不能是同义词。
3. 行数只用于事后核对「拆完够不够小」，**不能用于决定切点**。

## ㉖ 验证工具有错，会伪装成被验证对象有错

**实测**（2026-11-17，T1 验收）：

一个探针要验「T1 之后 v3 字段还丢不丢」。它的断言列表里含 `lastChange`，
**但它的测试数据里根本没给 `lastChange`**。于是它报：

```
丢失：lastChange  ⇒ T1 的修复无效
```

**被验对象是对的（13/13 保留），错的是探针。**

**这条为什么值得单独记**：它是最容易骗过人的一种错。真缺陷会让你去查代码；
探针缺陷会让你去查**已经正确的代码**，而且查不出结果 —— 因为那里没有错。
最后你会得出「这个修复不成立」的结论，然后**推翻一个正确的修复**。

**判据**：
1. 验证脚本必须先断言**它给的输入确实包含所有它要检查的字段**
   （如 `Object.keys(supplied).length === EXPECTED_COUNT`，或反向断言「每个被检查的键都在输入里」）。
2. 否则「字段没被保住」与「字段没被给出」**无法区分**。
3. 报告一个「被验对象有缺陷」的结论前，先贴「我给了什么」。

**本次的落地**：`restore-graph-v3.mjs` 的 `--verify` 在动手前先打印
「数据自身含 107 处 v3 字段实例（这是本次要恢复的目标量）」，并把期望值改为
**跑一遍归一化函数**得出（`expectedFieldCount`），而不是数 JSON 里的键。
后者曾经把 4 个节点的 `evidence: []` 算成「应该有」，于是把「空数组不存」这个**正确行为**
报成了「恢复不完整」—— 同一个病的第二个变种。

## ㉗ 「生成一份数据给人看」与「写进生产状态」必须由两个命令分开

**实测**（2026-11-17）：为了把 v3 数据交给执行者，运行了一次生成脚本；
而那个脚本最后一行是 `writeFileSync` 到活 store。**本意是只读产出，实际覆盖写入。**

**判据**：脚本默认必须是「只输出」（`--stdout` / `--dry-run`），写盘必须显式 `--write`。
读要免费，写要付代价。

**本次的落地**：`restore-graph-v3.mjs` 的三档：

```
node scripts/restore-graph-v3.mjs            ⇒ dry run（默认只打印，不改任何文件）
node scripts/restore-graph-v3.mjs --write    ⇒ 真正写（先备份）
node scripts/restore-graph-v3.mjs --verify   ⇒ 备份 + 在临时副本上证明「能修」
```

**默认不写**不是谨慎，是**唯一安全的默认**：这个工具改的是用户的活 store，
而"我本来只想看看"和"我改了生产数据"之间，只差一个没加的 flag。

## ㉘ 「锁」必须锁它声称保护的东西

**实测**（2026-11-17）：goal 锁的注释写着「working on the goal is what the lock is protecting,
**not reporting progress on it**」，而实现对 goal 节点的**任何** `update` 都拒：

```
const touchesGoal = targetId === GOAL_NODE_ID || …
if (locked && touchesGoal && (op === 'update' || op === 'deprecate')) return fail('GOAL_LOCKED', …)
```

于是「报告进度」与「重定义目标」被同样拒绝，而**报告进度正是这张图存在的理由**。
恢复工具被迫 unlock → write → re-lock 才能写入 5 个 journey 字段。

**判据**：
1. 写锁之前先列出**它必须拒绝的字段**与**它必须放行的字段**，两者都写成测试。
   只写「拒什么」的锁会连不该拒的一起拒。
2. **未在任一列表里的字段必须默认拒绝** —— 否则将来新增的字段会自动绕过锁。
   默认方向必须是「不许改」，锁才叫锁。
3. 批量更新里只要夹带一个禁区字段就**整批拒绝**，否则「放行 A」会成为夹带 B 的侧门，
   而部分生效比拒绝更糟。

**本次落地**：`GOAL_DESTINATION_FIELDS` / `GOAL_JOURNEY_FIELDS` 两套 + 六条测试
（v229 ①–⑥），can-red 是清空 DESTINATION ⇒ ② 红。

## ㉙ 工具层白名单必须随 schema 一起扩展，否则能力只到 schema 为止

**实测**（2026-11-17）：`GraphNode` 支持 13 个 v3 字段，`graph.ts` 也实现了读写校验，
但 `memory_graph_update` 的工具 schema 只转发 7 个 v1 字段：

```
node: { id, title, nodeType, requirements, status, dependsOn, knowledgePointers }   // ← 到此为止
```

⇒ 图能「读」v3 却不能「写」v3，会话无法创建完整计划图。

**为什么第三处最容易被忘**：它不在同一个文件里。改类型在 `graph.ts`，改存储在 `graph.ts`，
改 schema 在 `index.ts` —— 前两处一起看得到，第三处在另一个文件的开头。

**判据**：每加一个持久化字段，必须同时检查三处：
```
(a) 类型定义      (b) 存储层读写      (c) 工具层 schema 是否转发
```
第三处没做时**不会报错**，只会在「有人试着写」时才暴露 —— 而那可能是几周之后。

**本次落地**：13 个 v3 字段逐个声明（不是 `additionalProperties: true`，那会失去校验），
新增 v230 ⑪–⑬ 三条测试，其中 can-red 是移除 `log_pointers` 的转发 ⇒ ⑫⑬ 立刻红。

## ㉚ 三个文件之间的「挪来挪去」不减少总行数

**实测**（2026-11-17）：`graph.ts` 因新增 `constrain`/`relax` 涨到 919 行、超过 800 上限。
第一次处理是把它的一部分挪到 `graph-v3.ts` —— 于是 `graph-v3.ts` 也超过了 800。
**两个都红了，总行数一行没少。**

**真正解决它的是按语义切**：
```
graph.ts             788 行  owns the GRAPH
graph-v3.ts          655 行  owns the FIELD JUDGEMENT
graph-goal-lock.ts   171 行  owns LIFECYCLE
graph-view.ts         64 行  owns the RENDERED VIEW
graph-tool.ts        211 行  owns the TOOL SURFACE
```
这五个 `owns the X` **互不同义** —— 这正是 ㉕ 要求的检验。

**判据**：行数超限时，先问「这里有几个不同的职责」，而不是「哪一段可以搬走」。
**搬走**会让被搬去的那边也超限；**切开**才会减少总数。
